Generazione del mondo per VersMCBE

Catalogo delle opzioni prima delle domande. Obiettivo: entrando dal client Bedrock 1.26.60 si vede un mondo Minecraft "vero", generato con l'algoritmo Java Edition.

Cosa ho trovato

SteelMCServer Java in Rust, mira a Java 26.3. Il generatore confronta 7.500 chunk a caso con vanilla: tutti identici blocco per blocco. 10.201 chunk in circa 4 secondi su un Ryzen 9 9950X.
Mappature GeyserTabelle Java → Bedrock di blocchi (blocks.nbt) e biomi (biomes.json, 67 biomi). Generate per Java 26.3 e Bedrock 1.26.60: le stesse versioni di SteelMC e di VersMCBE. Licenza MIT.
BedrockData (pmmp)Definizioni complete dei biomi Bedrock e altri dati. Licenza CC0 (libera). Servono a sbloccare BiomeDefinitionList, che oggi fa chiudere il client.
Codice di SteelGeneratore: circa 70mila righe (29k in steel-worldgen, 41k in steel-core/worldgen). Dipende da steel-registry (79k), steel-utils (18k), steel-math. Esiste già ChunkMap::generate_region: genera un rettangolo di chunk fino allo stato finale.
ToolchainSteel usa Rust nightly fissato (nightly-2026-10-14) per SIMD e parking_lot. VersMCBE oggi è stable.
Salvataggio SteelFormato proprio "STLR", non Anvil né LevelDB Bedrock.

Trappole da sapere subito

AGPL + API per plugin

Copiando Steel, VersMCBE diventa AGPL-3.0. Hai detto che va bene. Però i plugin caricati dentro il server sono molto probabilmente "opere derivate": anche loro dovrebbero essere AGPL, e chi gestisce un server con plugin modificati deve offrirne il codice ai giocatori. PocketMine-MP usa LGPL proprio per lasciare liberi i plugin. Soluzioni:

  • Plugin fuori processo (WASM o processo separato con protocollo): l'isolamento rende più difendibile la libertà di licenza dei plugin.
  • Accettare plugin AGPL: semplice, ma scoraggia plugin commerciali.
  • Generatore in processo separato (opzione D sotto): il server resta MIT e solo il generatore è AGPL.

Non sono un avvocato: è un'indicazione, da verificare se il progetto diventerà pubblico o commerciale.

Nightly per tutto il progetto

Usando Steel come libreria, l'intero workspace passa a Rust nightly. Gli aggiornamenti di nightly a volte rompono la compilazione: si fissa la stessa data di Steel e la si aggiorna insieme a lui.

Il mondo non sarà quello di Bedrock vanilla

Con un seed avrai lo stesso mondo che vedresti in Java Edition, non quello di Bedrock (il generatore di Bedrock è chiuso e diverso). È quello che hai chiesto, lo scrivo solo per chiarezza.

Domanda 1: come portare dentro il generatore di Steel

Consigliata

A. Steel come libreria, con un adattatore nostro

Dipendenza git da steel-core fissata a un commit. Un nostro crate versmc-worldgen chiama generate_region e restituisce i blocchi Java già tradotti in Bedrock. Il resto di VersMCBE non vede Steel.

ProTutto incluso subito: terreno, grotte, acquiferi, alberi, minerali, strutture, villaggi, luce. Per aggiornare basta cambiare commit. Parità già verificata da loro.
ControSi compila tutto steel-core (circa 380k righe, anche la loro rete Java). Le loro API interne cambiano e l'adattatore va sistemato. Serve nightly.

Tempi: prima prova (compila e genera un chunk) in 1 sessione; mondo visibile nel client in circa 2-4 sessioni.

B. Copiare solo il generatore dentro VersMCBE

Si copiano steel-worldgen, steel-registry, steel-utils, steel-math e la cartella worldgen di steel-core, staccandola dal loro chunk, mondo ed entità.

ProSolo il codice che serve, controllo totale, compilazione più leggera.
ControCirca 150-200k righe da mantenere da soli. Ogni miglioramento di Steel va ricopiato a mano. Staccare le dipendenze interne richiede molto lavoro.

Tempi: parecchie sessioni solo per farlo compilare. Ha senso dopo A, se A diventa scomodo: l'adattatore rende il passaggio locale.

C. Solo il terreno, per gradi

Si prende solo steel-worldgen: rumore, funzioni di densità, biomi, regole di superficie, acquiferi. Alberi, minerali e strutture arrivano dopo.

ProPezzo piccolo e capibile. Montagne, oceani, fiumi e biomi arrivano presto.
ControIl mondo resta "nudo" (niente alberi né villaggi) a lungo. Le parti mancanti sono proprio quelle legate a steel-core: alla fine il lavoro è quello di B.

D. Generatore in un processo separato

Un piccolo programma basato su Steel (oppure un server Java vanilla con Chunky) genera i chunk. VersMCBE li riceve o li legge da disco.

ProIl server resta MIT e stable: i plugin non sono toccati dall'AGPL. Si possono anche importare mondi Java veri.
ControDue programmi da avviare, un protocollo tra loro, latenza in più. Con vanilla Java serve Java installato e il mondo va pregenerato.

Domanda 2: quale generatore gira nel processo separato

Hai scelto D. In tutte le varianti il server VersMCBE resta MIT e su Rust stable. Se Steel aggiorna, cambia solo il generatore.

Consigliata

D1. Un nostro piccolo generatore basato su Steel, su richiesta

Un programma versmc-gen (AGPL, nightly) usa steel-core come libreria. VersMCBE lo avvia da solo all'accensione e gli chiede i chunk ("dimensione, x, z") su un canale locale. Riceve i chunk già tradotti in blocchi e biomi Bedrock, con le mappature Geyser.

ProMondo infinito, generato mentre cammini. Seed scelto dal server. Un solo comando per avviare. Il protocollo tra i due è nostro e stabile, quindi aggiornare Steel non tocca il server.
ControDue binari da compilare (uno nightly). La compilazione del generatore è pesante. Un piccolo ritardo per ogni chunk nuovo, coperto da una coda e dalla cache.

Tempi: prova (genera un chunk e lo stampa) in 1 sessione; mondo nel client in circa 3-5 sessioni.

D2. Server Java vanilla + Chunky, poi leggiamo i file Anvil

Un server Java ufficiale con il plugin Chunky pregenera un'area. VersMCBE legge i file .mca, un formato stabile da anni.

ProÈ il generatore originale di Mojang, quindi parità garantita. Il lettore Anvil serve comunque per importare mondi Java esistenti.
ControArea finita: oltre il bordo non c'è niente. Richiede Java e il server di Mojang (EULA da accettare). Pregenerare richiede tempo: indicativamente minuti per 1.000 blocchi di raggio, ore per raggi grandi.

Utile più avanti come importatore di mondi Java, accanto a D1.

D3. SteelMC originale pregenera e leggiamo i suoi file

Scartata: il formato "STLR" di Steel è alla versione 23 e cambia spesso (strutture serializzate con wincode). Il lettore si romperebbe a ogni aggiornamento.

D4. VersMCBE si collega a SteelMC come un client Java

Scartata: servirebbe tutto il protocollo Java (in pratica un Geyser), e i chunk arrivano solo attorno a un "giocatore" finto.

Scelte che faccio io (correggimi se vuoi)

  • La traduzione Java → Bedrock avviene nel generatore: il server non vede mai ID Java.
  • Canale locale: socket TCP su 127.0.0.1 con messaggi binari a lunghezza fissa, avviato e fermato dal server.
  • Se il generatore cade, il server lo riavvia e intanto manda chunk vuoti invece di bloccarsi.

Domanda 3: come si salva il mondo

Scelta D1. Oggi nessuno modifica i blocchi, ma serviranno rottura e posa dei blocchi e i plugin. Il generatore D1 rifà sempre lo stesso chunk dallo stesso seed: va salvato solo ciò che cambia, o tutto per velocità. Il salvataggio lo fa il server (MIT), non il generatore.

Consigliata

S1. Formato mondo Bedrock (LevelDB)

Lo stesso formato di BDS e del gioco: cartella worlds/Mondo/db. In Rust c'è rusty-leveldb (MIT, 4.0.2, aggiornato a ottobre 2026), che supporta la compressione personalizzata necessaria per Bedrock (deflate, id 4).

ProIl mondo si apre in Bedrock, BDS, Amulet e Chunker. Puoi importare mondi Bedrock esistenti. Formato documentato da anni (PocketMine e Dragonfly lo usano).
ControTante chiavi e piccoli dettagli (sotto-chunk, biomi 3D, entità, versione). Più lavoro iniziale: circa 2-3 sessioni.

S2. Formato nostro, semplice

File regione 32×32 chunk, ognuno salvato con i byte che già mandiamo al client.

ProVelocissimo da scrivere (1 sessione) e da caricare: il chunk salvato è già pronto da inviare.
ControSolo VersMCBE lo legge. Per aprire il mondo nel gioco servirà poi un convertitore.

S3. Per ora non salvare niente

Ogni avvio rigenera dal seed; il salvataggio arriva insieme alla modifica dei blocchi.

ProZero lavoro adesso: si arriva prima al mondo visibile.
ControOgni chunk va rigenerato a ogni avvio. La decisione è solo rimandata.

Domanda 4: dove finisce questo primo traguardo

Scelte fatte: D1 (generatore nostro su Steel) e S1 (LevelDB Bedrock). Ora decidiamo cosa deve funzionare quando diciamo "fatto". Il resto finisce in una lista per dopo.

Consigliata

T1. Camminare in un Overworld infinito e salvato

  • Generatore D1 avviato dal server, con seed nel file di configurazione.
  • Blocchi e biomi tradotti, BiomeDefinitionList completa (niente più crash).
  • Movimento: i chunk arrivano mentre cammini o voli, in modalità creativa.
  • Spawn calcolato come in Java, su terra asciutta.
  • Chunk salvati in LevelDB e ricaricati al riavvio.

Tempi: circa 6-9 sessioni in tutto. Prima l'audit, poi la prova del generatore.

T2. T1 + rompere e posare blocchi

Aggiunge lettura dei pacchetti di interazione, aggiornamento dei chunk agli altri giocatori e salvataggio delle modifiche. È la base minima per i plugin.

Tempi: circa 3-4 sessioni in più.

T3. T1 + Nether ed End

Steel li genera già. Servono il cambio di dimensione (portali o comando) e altezze diverse: il Nether di Bedrock è alto 128 blocchi, quello di Java 256, anche se il terreno sta sotto 128.

Tempi: circa 2-3 sessioni in più.

Fuori in ogni caso (per ora)

  • Entità generate (abitanti dei villaggi, animali): Steel non le include nel confronto con vanilla.
  • Contenuto di casse e altri blocchi con dati: le casse compaiono, il bottino arriva dopo.
  • Luce calcolata dal server: in Bedrock la calcola il client.

Domanda 5: rompere i blocchi in creativa o in sopravvivenza

Traguardo scelto: T1 + T2 + T3. Per T2 cambia molto se il giocatore è in creativa o in sopravvivenza.

Consigliata

M1. Solo creativa

Rottura istantanea, posa da qualsiasi oggetto in mano. Il server controlla che il blocco sia raggiungibile, aggiorna, salva e avvisa gli altri.

ProCirca 3-4 sessioni. Il mondo generato si può già esplorare e modificare per intero.
ControNon è ancora un gioco: niente drop, niente inventario vero.

M2. Anche sopravvivenza

Tempi di rottura per blocco e attrezzo, oggetti che cadono e si raccolgono, inventario con transazioni (ItemStackRequest), fame e danno da caduta minimi.

ProSi gioca davvero.
ControRaddoppia T2 (circa 7-10 sessioni). Servono entità oggetto, tabelle dei drop e il sistema di inventario di Bedrock, che è complesso. Mescola il lavoro sul mondo con quello sul gameplay.

Nota

Oggi i giocatori non si vedono tra loro. Con M1 aggiungo solo ciò che serve perché vedano i blocchi cambiati dagli altri. Vedere gli altri giocatori resta un lavoro separato.

Scartate

IdeaPerché no
Scrivere un generatore Java da zero dai JSON di MojangSteel l'ha già fatto con parità verificata: rifarlo richiede anni.
Generatore Bedrock vanillaCodice chiuso, nessuna implementazione pubblica fedele.
Pumpkin, Valence (altri server Rust)Non approfonditi: nessuno dichiara una parità verificata come Steel. Valence non ha un generatore vanilla.
Rumore Perlin fatto in casaNon darebbe un mondo "reale" come hai chiesto.

Il lavoro che serve con qualsiasi opzione

  1. Tabella blocchi Java → hash Bedrock, ricavata da blocks.nbt di Geyser al momento della compilazione.
  2. Biomi: tabella Java → ID Bedrock e BiomeDefinitionList completa da BedrockData. Risolve il crash attuale.
  3. Serializzatore di chunk reale: 24 sezioni con palette variabili (oggi c'è un solo chunk fisso, 2 bit per blocco).
  4. Movimento (PlayerAuthInput) e invio dei chunk attorno al giocatore mentre cammina, con una coda per non bloccare il tick.
  5. Generazione fuori dal tick (thread pool) e cache dei chunk.
  6. Salvataggio su disco: formato da decidere (prossime domande).
