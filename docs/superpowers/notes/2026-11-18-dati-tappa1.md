## 2. Stati canonici dei blocchi

File: `vendor/BedrockData/canonical_block_states.nbt` (2.365.370 byte).

- Formato: sequenza concatenata di compound radice, **NBT "network" (varint)**: radice tag 0x0a con nome vuoto (varint 0), stringhe con lunghezza varint, int/long zigzag-varint, short/float/double little-endian fissi. Non e' una lista: si legge finche' finiscono i byte.
- Ogni compound: `name` (String), `states` (Compound), `version` (Int, sempre 18168865 = 1.21.x-ish, uguale per tutti).
- Conteggio: **16913 stati**, **1356 nomi** distinti. Tipi dei valori in `states`: Byte 20188 (bool 0/1), Int 13771, String 24630. Chiavi di `states` gia' in ordine alfabetico in tutti gli stati.
- Il README dice "ID di rete = posizione nella lista": **falso dalla 1.26** (sono hash). L'ordine del file e' per blocco, poi per combinazione di valori; non ordinato per nome ne' per hash.
- Dominio per stato: ogni blocco e' il **prodotto cartesiano completo** dei valori delle sue chiavi (verificato su tutti i 1356 blocchi, 0 eccezioni; max 384 stati per blocco). Il dominio si ricava raccogliendo i valori distinti per chiave, nell'ordine di apparizione.
- Stato di default: il file non lo dichiara. Il **primo stato di ogni nome** e' l'unico con meta 0 in `block_state_meta_map.json` (lista di 16913 int, allineata per indice; 0 gruppi con piu' di un meta 0; 0 gruppi il cui primo stato ha meta!=0). Quindi default = primo stato del gruppo (es. torch -> `torch_facing_direction=unknown`, wall -> tutte `none`, `wall_post_bit=0`). Coerente con le voci "senza block_states" del creativo, ma **UNVERIFIED** contro il default reale di Mojang per tutti i blocchi.
- Verifica hash (FNV-1a su NBT LE `{name, states}`, radice senza nome, states ordinati, tipi Byte/Int/String preservati):
  - `minecraft:air` = **-604749536** (OK, indice 13094)
  - `minecraft:stone` = **-2144268767** (indice 2706, stati `{}`)
  - i 16913 hash sono tutti distinti (nessuna collisione).
- Altri file: `block_state_meta_map.json` (meta per stato), `block_properties_table.json` (durezza, opacita', luminosita', attrito: per nome blocco).

## 3. Oggetti creativi

Cartella: `vendor/BedrockData/creative/` con 4 file (= 4 schede del menu): `construction.json`, `equipment.json`, `items.json`, `nature.json`.

- Formato: array di **gruppi** `{group_icon, group_name, items}`. 26 + 29 + 45 + 27 = **127 gruppi**; **2116 voci** (615 + 367 + 705 + 429).
- `group_name`: chiave di localizzazione (`itemGroup.name.planks`); `""` con `group_icon: null` per gli oggetti senza gruppo (es. stick in items.json). L'indice di gruppo e' la posizione nell'array; la categoria e' il nome del file (la `creative_category` del pacchetto CreativeContent: construction=1, nature=2, equipment=3, items=4 - UNVERIFIED l'ordine).
- `group_icon`: o stringa (nome item) o oggetto `{name, block_states?}` o null.
- Voce di `items`: o **stringa** (nome, meta 0, stato di default) o oggetto con `name` piu' uno tra: `block_states` (base64 di NBT **little-endian con radice senza nome** = compound degli soli states; 527 voci), `meta` (int, danno/variante di oggetto non-blocco: 204 in equipment + 117 in items; es. bed 0..15), `nbt` (base64 NBT LE del tag dell'oggetto; 175 voci: enchanted_book 125, banner 17, firework_rocket 17, firework_star 16).
- Tutti i 527 `block_states` esistono come stato esatto in canonical_block_states (verificato, 0 mancanti).
- Nomi distinti: **1657**. Mancanti da `crates/server/data/items.txt` (1627 voci): **172**, di cui 171 sono Education Edition (`element_*`, `colored_torch_*`, `compound*`, `balloon`, `bleach`, `chemical_heat`, ecc.) e 1 `minecraft:rapid_fertilizer`. Nessun nome del creativo manca in `required_item_list.json`.
- Al contrario: **109 oggetti di items.txt (1.26.6x) non esistono nei dati 1.26.30** e quindi mancano nel creativo e negli stati: 16 x cushion, 16 x wool_stairs, 16 x wool_slab, 16 x concrete_stairs, 16 x concrete_slab, e 29 altri (famiglia `poplar_*`, frostbite_spawn_egg, ice_ball, ice_crystal, icicle, red_shrub, shelf_mushroom, straw_bed, ...). Anche i blocchi corrispondenti (poplar_planks, pink_cushion, icicle...) **non sono in canonical_block_states** -> non si possono posare con questi dati.
- Altri file utili: `required_item_list.json` (1934 voci: `{runtime_id, component_based, version, component_nbt?}`; 73 con `component_nbt` base64 NBT LE).
- **ID numerici**: `required_item_list.json` ha ID della 1.26.30; 528 dei 1518 nomi in comune hanno un ID diverso da items.txt (es. acacia_boat 411 vs 382, acacia_door 595 vs 566: scarto ~29). Per gli ID usare SOLO items.txt; da BedrockData prendere solo i nomi.

## 4. Oggetto -> blocco

- `block_id_to_item_id_map.json`: 1322 coppie blocco -> oggetto. Solo 17 differiscono (`minecraft:bed` -> `minecraft:item.bed`, beetroot, brewing_stand, cake, camera, campfire, cauldron, flower_pot, frame, glow_frame, hopper, kelp, nether_sprouts, nether_wart, reeds, soul_campfire, wheat): sono nomi legacy usati per salvare su disco; l'oggetto vero di rete e' `minecraft:bed` ecc. Nessun oggetto compare due volte.
- 34 blocchi canonici non sono nella mappa (porte, hanging sign...): il nome oggetto = nome blocco.
- Regola pratica verificata su items.txt: dei 1627 oggetti, **1015 hanno nome uguale a un blocco canonico** (stesso nome -> stato di default, o lo stato esplicito se la voce creativa ha `block_states`); **612 non sono blocchi** per nome. Nessun oggetto di items.txt e' mappato a un blocco di nome diverso dalla mappa.
- Blocchi canonici senza oggetto in items.txt: 341 (air, `*_double_slab`, `*_standing_sign`, `*_wall_sign`, `*_candle_cake`, carrots, cocoa, cave_vines*, bubble_column, camera, ...). Sono blocchi "non oggetto": ok.
- Buco noto: oggetti che piazzano un blocco di nome DIVERSO (wheat_seeds -> wheat, redstone -> redstone_wire, sugar_cane -> reeds, oak_sign -> standing/wall sign, string -> tripwire, ecc.) **non sono nei dati BedrockData**. Fonte candidata: componente `minecraft:block_placer` in `bedrock-samples/behavior_pack/items` - **UNVERIFIED** (non l'ho trovato in locale; `required_item_list` non lo contiene nei component_nbt letti).
- Blocchi con stato non-default in creativo: tutti presenti in canonical (0 mancanti). Voci con `meta` su nomi di blocco: solo `bed` (15; il letto e' un oggetto con meta = colore, non un blocco con stato).

## 5. Dati giocatore nei mondi BDS (LevelDB, chiave `db/`)

Chiavi (verificate dal sorgente di Dragonfly `server/world/mcdb/db.go` e di cjwatson/minecraft-convert-local-player, entrambi MIT):

- `~local_player`: NBT LE, un solo compound radice = il giocatore locale (mondi giocati in locale, non BDS). Ha precedenza sui dati di level.dat (wiki).
- `player_<id>`: record di **mappatura** (NBT LE, compound) con 3 stringhe: `MsaId`, `SelfSignedId`, `ServerId`. `<id>` e' l
- `ServerId` = stringa `player_server_<uuid>` (la chiave intera, prefisso incluso). `<uuid>` e' un UUID generato dal server, non l'identita' del client.
- `player_server_<uuid>`: NBT LE con i dati veri del giocatore (stessa struttura di `~local_player`). Qui stanno anche `SpawnX/Y/Z` (Int; Dragonfly li legge qui).
- Per cercare giocatori nuovi: chiavi che iniziano per `player_` ma non `player_server_`.
- XUID: nessuna chiave per XUID trovata nelle fonti. UNVERIFIED (PMMP salva `LastKnownXUID`, ma e' un formato Java-like).
- Caso login senza Xbox (SelfSignedId, `online-mode=false`): UNVERIFIED (si presume MsaId vuoto/assente).

Campi NBT del giocatore (fonte: minecraft.wiki "Bedrock Edition level format/Entity format" e "/Item format"; **tutti UNVERIFIED su un mondo vero**):

| Campo | Tag | Note |
|---|---|---|
| `Pos` | List(Float) x3 | x,y,z; piedi o occhi? UNVERIFIED |
| `Rotation` | List(Float) x2 | yaw, pitch (gradi) |
| `UniqueID` | Long | |
| `DimensionId` | Int | 0 overworld, 1 nether, 2 end |
| `PlayerGameMode` | Int | nome usato dal wiki; `PlayerGameType` (nome richiesto) e' quello di level.dat: leggere entrambi, UNVERIFIED |
| `Inventory` | List(Compound) | solo slot occupati, ognuno con `Slot` Byte + stack; 36 slot (0-8 hotbar) |
| `Armor` | List(Compound) x4 | testa, petto, gambe, piedi; un stack ciascuno (presenza di `Slot` UNVERIFIED) |
| `Offhand` | List(Compound) | 1 stack; `Mainhand` idem |
| `EnderChestInventory` | List(Compound) | 27 slot |
| `SelectedInventorySlot` | Int | slot hotbar scelto |
| `SelectedContainerId` | Int | "da testare" nel wiki |
| altri | | `PlayerLevel` Int, `PlayerLevelProgress` Float, `SpawnX/Y/Z` Int, `SpawnDimension` Int, `SpawnBlockPositionX/Y/Z` Int, `Sleeping` Byte, `Sneaking` Byte, `Abilities` Compound, `recipe_unlocking` Compound |

Stack oggetto: `Name` String ("minecraft:..."), `Count` Byte, `Damage` Short (meta/variante), `Slot` Byte (solo negli elenchi di inventario), `WasPickedUp` Byte, `Block` Compound (opzionale: stato del blocco piazzato; sotto-campi presumibilmente `name`/`states`/`version`, UNVERIFIED), `tag` Compound (opzionale: incantesimi, nome, durabilita' come `Damage` Int), `CanPlaceOn`/`CanDestroy` List(String) opzionali.

## 6. Schizzo script di estrazione (stile extract_biomes.py)

Convenzioni: docstring italiana con Uso/Fonti, stringa `LICENSE` in testa, output JSON `{"_license": ..., "<lista>": [...]}` con `indent=1`, `sys.exit(msg)` su incoerenze, riga finale di conteggio. Argomenti: `<pmmp/BedrockData> <out>`.

`tools/extract_blocks.py <BedrockData> crates/server/data/blocks.json`:
- legge `canonical_block_states.nbt` con lettore NBT varint (tipi 1/3/8), ricalcola l'hash FNV-1a LE e controlla air = -604749536 e l'unicita' degli hash; verifica il prodotto cartesiano per blocco.
- uscita: `{"_license":..., "blocks":[{"name":"minecraft:oak_stairs","default":<hash>,"states":[{"key":"upside_down_bit","type":"byte","values":[0,1]},...]}]}`; per gli stati usare chiave+tipo+valori nell'ordine del file; l'hash di uno stato si ricalcola a runtime con `block_hash`. Se serve il meta (ricette): aggiungere `meta` da `block_state_meta_map.json`.

`tools/extract_creative.py <BedrockData> <items.txt> crates/server/data/creative.json`:
- legge i 4 file in `creative/` (scheda = nome file), decodifica `block_states` e `nbt` (base64 -> NBT LE), verifica ogni `block_states` contro i canonici.
- uscita: `{"_license":..., "groups":[{"tab":"construction","index":0,"name":"itemGroup.name.planks","icon":{"name":..,"block_states":{..}|null}}], "items":[{"tab":..,"group":0,"name":"minecraft:oak_planks","meta":0,"block_states":{..}|null,"nbt_b64":str|null}]}` (nbt lasciato in base64 se si rimanda al client cosi' com'e').
- ordine = ordine dei file (e' l'ordine del menu). Scartare i nomi fuori da items.txt (172, Education) stampando l'elenco; segnalare i 109 oggetti di items.txt assenti dai dati.
- ID oggetto da items.txt, mai da `required_item_list.json`.

## 7. Rischi principali

1. Dati BedrockData fermi a 1.26.30 mentre client e items.txt sono 1.26.6x: 109 oggetti (poplar, cushion, wool/concrete stairs/slab, icicle...) e i loro blocchi mancano; stati cambiati nel frattempo darebbero hash diversi da quelli del client. Verificare con blocchi noti in gioco.
2. ID oggetto: `required_item_list.json` e' sfasato (~29) rispetto a items.txt: non mescolare le due fonti.
3. Default di stato dedotto (primo del gruppo / meta 0), non dichiarato; gli oggetti che piazzano blocchi di nome diverso (semi, redstone, cartelli, canna) non hanno fonte.
4. `PlayerGameMode` vs `PlayerGameType`, `Pos` piedi/occhi, forma di `Armor`, sotto-campi di `Block` vanno verificati su un mondo BDS vero; nessuna fonte per il caso senza Xbox ne' per l'XUID.
5. Il README di BedrockData (ID = indice) e' obsoleto dalla 1.26; il creativo ha 171 voci Education da filtrare e CreativeContent 1.26.6x puo' richiedere campi (categoria/ordine gruppi) assenti nei JSON.
