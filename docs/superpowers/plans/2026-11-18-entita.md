# Tappa 2 "entità e giocatori" Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Gli altri giocatori diventano visibili (lista, corpo, movimento, animazioni, skin) e nasce il primo tipo di entità non giocatore, l'oggetto a terra (lancio con Q, raccolta), sopra un registro unico delle entità; `/bot` permette di provare tutto con un solo account.

**Architecture:** Un registro `Entities` nel `Server` (mappa ID runtime → `Entity` con tipo enum e dati comuni). I giocatori collegati usano come ID runtime il loro `pid` (già usato in `StartGame`); le altre entità prendono ID da 2^32 in su, così lo spazio è unico. La visibilità si ricalcola ogni tick: un giocatore vede le entità nei chunk del suo `sent`, tranne se stesso; le differenze generano comparse (`AddPlayer`/`AddItemActor`) e rimozioni (`RemoveActor`). Movimento e stato si mandano ai soli spettatori, al massimo una volta per tick.

**Tech Stack:** Rust (workspace `crates/protocol`, `crates/server`), protocollo Bedrock 2225, test unitari con `Harness` (`crates/server/src/tests.rs`).

**Spec:** `docs/superpowers/specs/2026-11-18-entita-design.md`

## Global Constraints

- Protocollo 2225 (client 1.26.6x). Gli schemi Mojang in `vendor/bedrock-protocol-docs/json` (tag v1.26.65) sono l'autorità sui byte; Dragonfly 1.26.60 (`vendor/dragonfly`) sull'ordine dei pacchetti e sul comportamento.
- Varianti con etichetta (`oneOf` con `x-control-value-type`) = indice di variante varuint32, poi il corpo; se il corpo comincia con un campo tipo `Enum-as-Value` (es. `DataItemType`, `ItemStackRequestActionType`) quel byte c'è anche lui (verificato sulle catture). Come `crates/protocol/src/actor.rs`.
- Flag delle entità dopo CAN_DASH(46): collisioni 48, gravità 49 (changelog_560). Chiavi dati: FLAGS 0, BOUNDING_BOX_WIDTH 53, BOUNDING_BOX_HEIGHT 54.
- `generated.rs` non si modifica a mano: si rigenera con `python tools/protocolgen.py vendor/bedrock-protocol-docs/json crates/protocol/src/generated.rs <elenco>` (elenco attuale nel README, sezione "Pacchetti generati"; aggiungere i nuovi in fondo e aggiornare il README). Pacchetti che il generatore non sa fare (`oneOf`, pelle) si scrivono a mano in `crates/protocol/src/entity.rs` o `skin.rs`.
- Le codifiche non confermabili dai test si loggano in esadecimale per le prime `HEX_LOGS` (3) volte per giocatore e finiscono nella lista di verifica nel gioco.
- La skin si manda solo nella `PlayerList` (e in `PlayerSkin` quando cambia), mai in `AddPlayer` né a ogni comparsa.
- Il proprio corpo non si manda mai a se stessi.
- Ciclo unico a 20 Hz (`Server::tick`), nessun thread nuovo.
- Commenti e log in italiano; rustfmt 160; `cargo clippy --workspace --all-targets -- -D warnings` pulito; `cargo test --workspace` verde; commit che terminano con `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>` (o il modello che lavora).
- Licenze: server MIT; nessun codice dal generatore AGPL; dati e comportamenti da Dragonfly (MIT) citati nei commenti.

## Review Focus

1. Un giocatore esce mentre altri lo vedono → per tutti `RemoveActor` e rimozione dalla `PlayerList`; nessun fantasma. (Test in Task 4.)
2. Un giocatore entra quando altri sono già dentro → riceve la lista completa e i corpi di chi è nei suoi chunk, e gli altri ricevono lui; nessuno riceve se stesso. (Test in Task 4.)
3. Due giocatori sono sopra lo stesso oggetto nello stesso tick → lo raccoglie uno solo; nessuna duplicazione. (Test in Task 9.)
4. Login senza skin o con skin malformata (campi mancanti, base64 rotto) → il giocatore entra comunque con una skin di ripiego, nessun crash. (Test in Task 2.)
5. Oggetto lanciato in un chunk che poi esce dalla vista di tutti, o che cade fuori dal mondo (sotto y = -64) → niente comparse orfane; sotto il mondo l'oggetto sparisce. (Test in Task 8.)
